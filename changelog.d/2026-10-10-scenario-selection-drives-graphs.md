---
type: fixed
area: Scenario & run selection
user: Selecting a scenario now switches both graphs to it straight away (showing its latest run), instead of leaving them on the previous scenario until one of its runs is clicked.
---
Old bug mechanism: `ScenarioBrowserViewModel::activateScenario` only stored the active hash/name and reloaded the run list; nothing changed the session's current run, and both graphs follow the current run (`GraphUseCase::onCurrentPerfChanged`, `CompletionHistoryUseCase::onCurrentScenarioChanged`), so after selecting "Pasu Gallery" the per-run graph and the history graph kept showing "1wall6targets Gallery" until a Pasu run was clicked. The QML also kept the active scenario as local state in `SelectionPanel.qml` / `ScenarioSearchPanel.qml`, set on click, so a Recent run of another scenario left the list on the old scenario while the graphs moved.
New `IScenarioBrowserUseCase::selectScenario(ScenarioId)` (contracts, Qt-free): `ScenarioBrowserUseCase` makes the scenario's most recent run current via `IProfileService::getMostRecentRun` + `ISessionController::setCurrentRun(run_id)`; it is a no-op when the current run already belongs to the scenario (so re-clicking the scenario of a picked run keeps that run), for an empty hash, and for a scenario without runs.
`ScenarioBrowserViewModel::activateScenario` now calls it after updating the active scenario (VM still talks only to the use case, ADR 0004).
The VM's active scenario also follows the current run: `refreshCurrentRun()` activates the current run's scenario when the current run changes to a run of another scenario (Recent selection, File > Load Performance, latest run after an import). Only an actual current-run change moves it, so a refresh for any other reason never overrides the user's choice. On construction this means the browser starts on the scenario the graphs show.
`refreshScenarioModel()` clears the active scenario if it disappears from the catalogue (rebuilt/cleared profile) rather than listing a scenario that no longer exists.
New VM properties `activeScenarioName` (NOTIFY `activeScenarioChanged`) and `hasScenarios` (unfiltered catalogue non-empty, NOTIFY `hasScenariosChanged`; used by the first-run welcome). `ScenarioWorkspace.qml` binds `activeScenarioHash`/`activeScenarioName` into `SelectionPanel`, which no longer assigns them on click; `ScenarioSearchPanel.currentScenarioHash` is likewise bound, not assigned.
`RunListModel` gained a `scenarioName` role (`ScenarioNameRole`) for the Recent list's scenario column.
Architecture view `docs/architecture/views/runtime/run-selection-and-rendering.md` gained a "Scenario activation" section and invariant.
Tests: `ScenarioBrowserUseCaseTest.SelectScenario*` (app), new `ScenarioBrowserViewModelTest` cases for activation, following the current run, keeping a user activation across refreshes, clearing a vanished scenario, `hasScenarios`, and the `scenarioName` role (ui-cpp), and the integration test `ScenarioSelectionUiTest.ActivatingAScenarioMovesBothGraphsToIt`, which imports two fixture scenarios through the real pipeline and checks both graph view models' titles after `activateScenario`.

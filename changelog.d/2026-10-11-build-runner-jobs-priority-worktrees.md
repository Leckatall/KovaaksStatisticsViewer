`scripts/build_and_test.py` build parallelism and process priority are now machine-local settings, and linked git worktrees share the main checkout's `toolchain.local.env`.
New runner keys `KSV_BUILD_JOBS` (positive integer, default 8) and `KSV_BUILD_PRIORITY` (`normal` | `below_normal` | `idle`, default `normal`) live in `scripts/toolchain.defaults.env` and layer exactly like the toolchain keys: defaults, then `toolchain.local.env`, then process environment. They replace the hard-coded `orchestrator.BUILD_JOBS = 8`.
`config.py`: `RUNNER_KEYS` sit beside `TOOLCHAIN_KEYS` (the env-file reader accepts both), resolved by the new `resolve_runner_settings()` into a `RunnerSettings(jobs, priority)` that `run_pipeline` takes as a required argument. The settings are deliberately kept out of `Toolchain` and `build_fingerprint`, so changing the job count or priority never wipes `build-agent/`. Invalid values fail with a `ToolchainError` naming the key and the bad value.
Priority is applied as a Windows priority class via `creationflags` on every process `run_command` starts (configure, build, every test runner). Children of a below-normal or idle process inherit its class, so ninja's compiler processes and ctest's test executables run at that priority too (verified: child and grandchild both report `0x4000`).
`--jobs` stays unrecognized on purpose (`test_jobs_is_not_a_public_option`): parallelism belongs to the machine, not to whoever invokes the runner.
Worktrees: `find_local_env()` returns this checkout's `scripts/toolchain.local.env` if present, otherwise the main worktree's, located with `git rev-parse --git-common-dir` (`main_worktree_root()`; returns None outside a repo, for a bare repo, or when git is missing). `resolve_toolchain` uses it, so `ui_driver.py` and the runner both pick it up; the runner prints `local overrides: <path> (main worktree)` when the fallback is used. A worktree can still override by creating its own file. Previously a new worktree (Claude Code, `git worktree add`, CLion) had no local file, so the runner fell back to the canonical paths in `toolchain.defaults.env`, which point at another machine, and failed with a toolchain "not found" error until the file was copied in by hand.
`scripts/toolchain-config.ps1` (used by `package-release.ps1`) accepts the two runner keys without using them, so adding them to `toolchain.local.env` does not break packaging, and gained the same main-worktree fallback in `Find-KsvToolchainLocalEnv`.

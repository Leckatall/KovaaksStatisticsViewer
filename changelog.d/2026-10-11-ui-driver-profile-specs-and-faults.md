Two general UI driver mechanisms so niche data and error states need a spec or a flag, not driver code. Reference: `tools/driver/README.md`.
`start --profile-spec FILE.json` builds the session's `profile.pb` from a declarative spec (`tools/driver/driver_spec.*`; example `tools/driver/specs/many-scenarios.json`):
- Per scenario: `name`, optional `hash` (default `spec-<slug>`), `runs`, `firstDay`/`daySpacing`, `runsPerDay`, `startMinute`/`minuteSpacing`, `durationSeconds`, `performance` (false leaves `Run::performance` empty with totals only, so the run graph shows `graphNoPerformanceLabel`), and `shape` (a gallery shape name or an object of base values).
- Top level `benchmark`: a path to a benchmark JSON to copy, or an object (`id`, `name`, `file`, `tiers` or `tierFactors`, `categories` naming scenarios by name or name + hash). Thresholds sit at each tier factor x the scenario's personal best; a name not in the profile becomes an unresolved entry (no hash) around a nominal 1000.
- Unknown fields and bad values fail with their path (`scenarios[3].runsPerDay: expected an integer >= 1`) before the app starts.
- Deterministic: each run is seeded from its scenario and run index, scenarios are generated in order, and the store's `created_at` is pinned to 2026-08-01 by seeding a header-only `profile::File` before `ProfileSerializer::save` (which keeps an existing store's `created_at`). The same spec writes the same bytes; no `src/` change.
- The spec replaces the profile, so it combines only with `--dataset empty`, `first-run` or `fixtures` (with `--profile-spec`, `start` defaults to `empty`). Order: dataset seed, profile spec, overlays, driver defaults, settings.
- `gallery_dataset.h` now exposes `RunShape`, `shapeForHash` and `makeRun` (pure code motion; the built-in profiles are byte-identical apart from the save timestamp). The demo benchmark is now `generateBenchmark(profile, demoBenchmarkSpec())`, the same generator specs use. `DriverSpecTest.BuiltInDatasetsAreUnchanged` pins each built-in dataset's run count, scenario set, first/last start time and total score.
`start --inject PORT[.OP]=EFFECT[,EFFECT...]` (repeatable) wraps the services the driver hands to `App`'s injecting constructor in decorators (`tools/driver/driver_ports.*`): `decoder` (`decode`, `decode_file`; failure = a thrown `std::runtime_error`, as `ProtoDecoder` does), `csv` (`parseFile`; `std::nullopt`), `benchmarkStore` (`scan` -> `DirectoryUnavailable`, `write`/`remove` -> `WriteFailed`) and `seriesStore` (every mutation plus `commitDraft` -> `PersistenceWriteFailed`). Effects: `delay:MS`, `fail`, `fail:N` (only the Nth call), `fail:after:N`. A port the plan does not name is passed through undecorated. Each injection is logged once at startup (`ksv_driver: inject benchmarkStore.write=fail`), recorded in `session.json` and listed by `status`; the CLI validates the grammar before launching.
Thread map, for `delay`: `decoder.decode_file` and `csv.parseFile` run on `SessionController`'s worker thread during full profile builds and on the GUI thread for live imports and Load Performance File; `benchmarkStore` and `seriesStore` always run on the GUI thread, so a delay there freezes the UI for that long.
`ksv_driver` now sets `QT_FORCE_STDERR_LOGGING=1`: detached from a console, Qt on Windows sent every qDebug/qInfo/qWarning to `OutputDebugString`, so none of them reached `app.log`.

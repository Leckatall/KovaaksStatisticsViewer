---
type: fixed
area: Benchmarks
user: In the Benchmark Manager, hiding the library list and showing it again no longer leaves the rank columns scrolled sideways with the first rank out of view and an empty gap before the add-rank "+". When every rank fits they are all shown from the first; when they don't, the table stays scrollable to every rank and keeps the position you scrolled to.
---
Bug mechanism: `BenchmarkEditorTable.qml` hides the identifying columns inside `thresholdView`'s own column space with a negative `leftMargin` of `thresholdKind * thresholdWidth`, so the first rank starts at `contentX == -leftMargin`. When the rank width changed (the library toggle widens and then narrows the table, which changes the equal share per rank), `relayoutRankColumns()` runs a `Qt.callLater` after the change and computes the scrolled rank count as `(contentX + leftMargin) / previousWidth`. But `leftMargin` was a live binding that had already moved to the new width, while `contentX` was still in the old coordinate space. Widening was harmless (the result clamped to 0, and Flickable's own fixup pulled `contentX` up to the new start), but narrowing back left `contentX` at the wider width's start, which the computation read as `3 * (wide - narrow) / wide` ranks scrolled; the view was then placed that far in, showing Bronze first with blank space past Platinum, and no scrollbar since the ranks fit.
Fix: `hiddenThresholdWidth` (both views' `leftMargin`) now follows `laidOutThresholdWidth` once the first layout has happened, so the margin only changes inside `relayoutRankColumns()`, together with the rebuild; until then `contentX` and the margin stay in the same space, and the scrolled rank count is measured against `thresholdKind * previous`. This also stops the rank columns jumping sideways by the margin difference while a cell editor defers the relayout.
New `rankScrollStart` / `rankScrollRange` (computed from `rankColumnsWidth - availableRankWidth`, not from the view's own width, which a layout polish may not have updated yet) bound the horizontal position: the relayout places the view at `start + min(scrolledRanks * width, range)`, so ranks that fit always start at the first, and `clampRankScroll()` (run through `relayoutRankColumns()` whenever the range changes, e.g. a dialog resize or a rank added or removed while the width stays at the header minimum) pulls an out-of-range position back to the nearest edge and leaves an in-range one, such as the user's own scroll, untouched. Nothing moves under an open cell editor; the clamp runs when the edit ends.
Tests: `tst_BenchmarkEditorTable.qml` `test_narrowingWhileTheRanksFitShowsThemFromTheFirst` (fails before the fix: contentX 518 against a start of 372 after 1100 -> 1500 -> 1100) and `test_overflowingRanksKeepAReachableScrollPosition` (an end position stays within range after widening while still overflowing; a mid position survives a narrowing).

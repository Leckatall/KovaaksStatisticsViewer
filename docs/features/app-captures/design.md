# App captures — software design

## Purpose and design scope

This document designs the capture capability governed by [App captures requirements](requirements.md). It covers all six graph targets and the benchmark tracking table: taking a snapshot of selected values, rendering a clean image, reviewing its size, copying it, saving PNG, and reporting outcomes. It defines responsibilities, contracts, lifecycle, and completion criteria for implementing the feature as a whole. It does not implement the feature or prescribe a file-by-file implementation plan.

The owner confirmed the design direction before synthesis. Copy from the preview keeps that preview open and uses its reviewed image; Export closes it when a PNG destination is confirmed and reports the background outcome in the main status bar. The requirements have been reconciled to those decisions. A later review against the code settled the implementation approach recorded under [Architectural decisions](#architectural-decisions). The design was approved on 2026-11-01; the numeric limits and standard graph reference size stay open until the validation gate.

## Technical drivers

- One camera activation must produce a useful image with defaults and no preview visit.
- Selected information and its interpretation must survive independently of the live view models and later imports, selection changes, configuration changes, or date rollover.
- Resolution changes raster detail; they must not reveal more data, change bounds, or alter the logical layout of an otherwise unchanged capture.
- A full table can exceed both viewport dimensions. Completeness and readable labels govern its layout; practical limits govern whether the complete image is supported.
- Copy retains the preview; committing a destination dismisses it before saving finishes. Output work and its feedback must therefore outlive a dialog.
- Background rendering must not access QML items, mutable QObjects, or callbacks closing over live model state.
- Output must have an observable success/failure result, with no premature success, deliberately cleared clipboard on failure, or partial PNG replacement represented as success.

## Proposed design and delta

Add a presentation-owned capture coordinator with one current preview session. One graph source reads the effective state from the live `GraphCanvas`, and one table source reads the benchmark presentation; each panel supplies only its own context. Both take a value snapshot. A dedicated C++ renderer measures those values once, in logical units, into a flat list of positioned items, then paints that list into a new image at the requested pixel size. The live graph paints through the same graph path, while the renderer owns export composition: titles, identifying context, passive legends, and complete table layout.

The same source, layout, renderer, and output path serve quick copy and the preview. Quick copy creates an ephemeral session with 200% resolution and the benchmark summary included. Preview Copy submits its current successful render instead of creating a default capture or resampling the live widget.

Application use cases own clipboard and PNG output. They accept immutable raster values, not view models or QML items, and retain each accepted operation independently of the preview. Output adapters perform platform work and return explicit outcomes. No accepted-data service, persistent capture preference, or image library is introduced.

## Interfaces and interactions

### Taking the value snapshot

Capture sources distinguish `run`, `dailyPlaytime`, `scenarioHistory`, `benchmarkRank`, `benchmarkRecentRank`, `benchmarkPlaytime`, and `benchmarkTable`, the benchmark tracking table. A graph key is not a series position or a selected benchmark identifier. Series continue to use stable IDs/column values.

The table has no settings action of its own, so its camera and dropdown sit in the pinned benchmark header beside the picker, as in the [approved mockup](../../../.designs/2026-11-01/widget-image-export/final/02-benchmark-menu.png). That header serves both trackable and incomplete benchmarks.

The normal capture action handler reads the current presentation values once into an owned snapshot. Ordinary GUI event handling already keeps another user-input handler from running partway through that synchronous read; this needs no special input-blocking behavior, application-wide lock, or pause of imports or live updates. After the read, the app continues normally while rendering uses the copied values. Only the snapshot stays unchanged for the preview visit.

A graph capture reads the `GraphScene` from the target's `GraphCanvas`, so the snapshot cannot disagree with what the canvas paints and all six graphs share one adapter. The panel adds what the canvas does not hold: its title, X label, and interval. The camera sits beside the settings action, outside the `Loader` that holds the canvas, so it reaches the canvas through the loader's item; no item means the target is unavailable.

The snapshot includes the context belonging to those values. Any missing run/date metadata should come from the presentation model's ordinary application projection, so capture does not have to recalculate data or query a later selection to label an earlier result.

The source reports unavailable content explicitly. A line-mode rank graph with carried state can be meaningful even with no in-range improvement observations. Points-only mode with no drawable observations cannot manufacture points from that carry. An unplayed benchmark row with explicit statuses is still table content; an absent or empty usable table is unavailable. An incomplete benchmark's table can be captured and carries a concise "not ready to rank" note. While `summaryAvailable` is false the summary is omitted and its preview option is disabled.

### Quick copy

1. Admit the camera request if no capture preparation or output is running. A repeat of the same action on the same target is ignored as an accidental double-activation; any other rejected action reports a normal one-line result through the shared status feedback, such as "Another image is still saving". Record the originating target and take a snapshot of its current values.
2. Build the standard reference layout, default options, and measured output request. Validate layout and resource policy before large allocation.
3. Render at 200%, then submit that immutable result through the output use case. No preview or save dialog opens.
4. Publish success only after clipboard publication is confirmed. Preparation, render, or clipboard failures use the shared status feedback and leave the main app usable, with Export image available for adjustment.

### Preview and Copy

The preview is a window-modal `ApplicationWindow` over the main window, with `flags: Qt.Dialog` and `palette: Theme.palette`, following [SettingsDialog](../../../src/ui/qml/shell/SettingsDialog.qml). Only one preview can exist. Imports and live updates continue behind it while input to the main window is blocked, so a camera action cannot start during a preview visit or its save picker.

Opening Export image takes a new value snapshot and starts a local options session at defaults. Changes immediately invalidate the old render for output; validation and rendering produce a new generation. Only a successful render for the current generation enables Copy and Export. During a valid replacement render the previous image stays visible and cannot be output. A failed generation or an invalid request clears it, so neither can pass off the previous image as the reviewed result.

Copy pins the current rendered pixels and submits them through the same output use case as quick copy. It publishes synchronously on the GUI thread, so there is no pending Copy state to lock or display. If an earlier save is still running, Copy reports a one-line notice and changes nothing. Success and failure leave the preview open, preserving its snapshot, options, and valid image. Neither result returns focus to the main window merely to show a message. The shared status feedback is perceptible and dismissible in the preview context as well as in the main window.

Close, the window close action, and Escape remain available. They discard pending preview rendering or release the local session, without initiating output. Reopening starts a new snapshot and defaults; it does not recover a hidden prior visit.

### Export and save

Pressing Export first checks output admission. If an earlier save is still running, Export reports a one-line notice and no picker opens. Otherwise it pins the successful current render and opens the native PNG save dialog. The reviewed choices cannot change underneath the picker, and because the preview is window-modal, nothing else can start output while the picker is open. Declining overwrite leaves the picker open with the preview unchanged behind it. Canceling the picker releases that temporary action state and returns to the same preview. Neither reports an error.

Confirming the destination transfers the immutable image and selected local path to the output workflow and immediately closes the preview, restoring focus to its origin where that origin still exists. Completion remains associated with an operation ID, so even an immediate save-start failure is reported after dismissal. Closing is not a success signal.

Saving occurs in the background. No in-progress state is shown. Success or failure is announced in the main status bar. Failure does not reopen the dialog, retain a hidden editable snapshot, or silently retry. The user can start a fresh export visit. The operation retains its pixel buffer only as long as required to finish.

### Output contracts and completion

The output contract offers copy-image and save-PNG capabilities with immediate admission status and an eventual typed result. Results carry operation ID, target label, and a user-presentable failure category; save destination details are never painted into an image. Callback delivery is normalized onto the presentation thread, and completion is published once. Copy completes on the GUI thread but reports through the same result path as a save. Renderer results use a separate generation token so a late render cannot complete an output job.

The image is fully rendered before it reaches the clipboard adapter, and the adapter does not call clear as preparation or failure cleanup. Windows-format conversion is deferred: Qt publishes an OLE data object and converts on demand each time a reader requests a format, so a paste, clipboard history, a clipboard manager, or Qt's flush at normal exit can trigger it after success has been reported. An opaque 32-bit image offers only `CF_DIB`. An alpha-capable format would also offer DIBV5 and PNG, even with fully opaque pixels, and would encode PNG on demand, which is why the raster uses an opaque layout. Qt's [setImage API](https://doc.qt.io/qt-6/qclipboard.html#setImage) has no success return. The Qt-based candidate therefore verifies ownership of the submitted image after the call; returning from setImage or emitting a generic changed signal alone is insufficient. Ownership proves publication, not that every later conversion will succeed. The inspected [Qt 6.12 Windows backend](https://github.com/qt/qtbase/blob/6.12/src/plugins/platforms/windows/qwindowsclipboard.cpp) publishes through OleSetClipboard, releases its candidate on failure, and checks the current OLE object for ownership. That supports this candidate strategy, rather than a general guarantee inferred from the setter's signature. The public API and Windows behavior must be covered by the platform validation gate, including clipboard contention. Inability to confirm publication is a failure, not success inferred from a log message. The adapter does not promise transactional restoration of arbitrary pre-existing clipboard contents after every possible OS failure.

PNG output encodes the pinned image to [QSaveFile](https://doc.qt.io/qt-6/qsavefile.html), with direct-write fallback disabled. Encoding success and successful commit are both necessary for completion. A write/encode/commit failure discards temporary output and is reported through the operation result. Existing destination content is not intentionally truncated before a complete replacement is ready. Ordinary native overwrite confirmation precedes this operation; the feature adds no extra confirmation or destination conflict workflow.

## Data, state, and persistence

### Snapshot contents

| Snapshot | Required owned values |
| --- | --- |
| Common | Target kind and display name; scenario/benchmark identity as applicable; friendly identifying context; palette/background and the other `Theme` tokens export needs, supplied once from QML because `Theme` exists only there and copied into each snapshot; resolved fonts, locale/date formatting; source availability; standard layout policy inputs |
| Graph | Effective visible series in user line-list order; stable IDs/names/colours/widths; display-space observations and separate carried endpoints; resolved per-series axes and shared labelled-axis membership; every distinct displayed scale with its series, bounds, and units; bounds, tick positions and formatted labels; connection mode, marker preference, reference levels and their meaning; graph-specific X/Y titles and selected-range context |
| Benchmark table | Benchmark title; all rows, tiers, and group spans in displayed semantic order; full labels and formatted values; PB dates, play counts, thresholds, next-tier information; tier fills/colours, recent-average marker position/meaning, missing or exceptional states, blocker and group rank presentation; associated summary values and `summaryAvailable`; benchmark classification and a concise completeness note |

Resolve neutral graph colours against the captured foreground, as the live canvas does; axis grid and tick-label colours stay the live `AxisPainter::Style` values. Format every tick into its label at snapshot time, so no `std::function` from an axis reaches a worker: the existing [Axis](../../../src/ui/presentation/graphs/common/axes/axis.h) delegates formatting through [ValueTransform](../../../src/ui/presentation/graphs/common/axes/value_transform.h), whose callable storage by itself provides no lifetime guarantee. Export layout may select a readable subset of ordinary numeric ticks without changing bounds; required context, units, tier meanings, and references cannot disappear to make a layout fit.

The live graph labels one Y axis, and other series are readable only through the hover tooltip that captures exclude. The passive legend therefore lists every distinct displayed scale once, with its series, bounds, and units. Series sharing a `yAxisId` count as one scale.

Rank reference lines carry no name of their own: their meaning comes from the tier tick labels, and [AxisPainter](../../../src/ui/components/axis_painter.h) drops colliding labels by stride. Export keeps every shown tier label on rank axes, and dimensions that cannot fit them fail validation. The check is `layoutLabels` at reference geometry: fewer placements than ticks on a rank axis is the failure, so no separate keep-all mode exists.

The run graph identifies the selected run and its date through the existing run label, and labels elapsed time with units. Daily and benchmark histories state the displayed calendar interval, including selected boundaries beyond the last observation; the interval comes from the range the `DateTimeAxis` was given rather than its resolved bounds. Scenario history identifies the scenario, states that its X axis counts runs, and gives the dates of the first and last visible runs, which `CompletionHistoryViewModel` retains from `start_time_ms`. The scenario history's selected-run band is not captured. No source filesystem path is part of capture identity.

### Reference layout and output dimensions

Graph reference layout is a standard readable export composition independent of live widget dimensions. At 100%, it allocates a plot, required context, and passive legend using the captured appearance and content. Long titles or legends may enlarge this initial composition. Concrete standard dimensions and spacing are implementation latitude subject to the measurement/readability gate; mockup bitmap sizes are not production defaults. Once established for a visit, the reference is stable.

Let `s = resolutionPercent / 100` and let `Lw, Lh` be the logical reference dimensions. Normal output is `round(Lw × s)` by `round(Lh × s)` pixels. There is one rounding policy shared by layout validation, displayed dimensions, image allocation, clipboard, and PNG. At unchanged layout, 200% doubles both dimensions from 100%.

Advanced graph fields display final output pixels. Committing a valid explicit width or height at the current resolution updates the logical layout dimension to `pixels / s`; the percentage remains unchanged. With **Keep aspect ratio** enabled, its initial state, update the other dimension proportionally; without it, remeasure the new composition and reject insufficient room rather than shrinking required text. Subsequent percentage changes scale that edited reference. For example, at 200%, a custom 1800 × 1000 output establishes a 900 × 500 logical composition; 300% then requests 2700 × 1500. A short explanation beside the controls makes their relationship explicit. When a custom size leaves too little logical room, the error says whether larger dimensions or a lower resolution would provide it, and names a specific resolution only after validating that candidate.

Table layout measures all content. It allocates each identity/value column and tier chunk enough room for its headings and values, wrapping full labels and increasing row or group height when needed. There is one identity-column set, no pinning, no elision, and no scroll offset in the image. Group spans follow the resulting row heights. Tier fills, thresholds, PB/recent-average meaning, and exceptional states retain the live semantics.

Thresholds sit in their own lane under each row's bar, aligned to their chunks, so they never compete with the value label or the recent-average marker. A chunk is as wide as the wider of its tier name and that column's thresholds; when a value or status text needs more room than that bar provides, every chunk gains an equal share of the difference. The personal-best value stays on the bar under the same inside-or-past-the-fill rule as the live bar. Export therefore needs none of `TierBar`'s end/middle/start label placement or cut-marker logic. A threshold the live bar would hide behind its value label stays visible in the lane; hatched chunks and status rows stay empty, as they do live. The lane departs deliberately from the live bar and raises rows from about 30 to about 42 logical pixels. The owner approved the rendered result on 2026-11-02.

The benchmark title and headings are unconditional. Summary inclusion changes a separate measured summary region and therefore the reference/output dimensions, without changing table content. Table height and width remain content-derived; the preview exposes resolution and summary inclusion, not arbitrary fixed dimensions.

### Render and session state

| State | Preview and available behavior |
| --- | --- |
| Validating / rendering | Any previous image stays visible, without dimming or busy text, and cannot be output; options and Close remain available; output actions are disabled |
| Ready | Display the current successful image and exact pixel dimensions; enable applicable output actions |
| Invalid / unavailable / render failed | No image; retain snapshot and raw options; explain correction or retry; output actions stay disabled |
| Save picker | Preserve and lock the reviewed choices until destination confirmation or cancellation |
| Dismissed | No editable session remains; accepted output jobs independently retain required pixels and publish feedback |

Every options change increments the render generation and coalesces pending work to the latest request. Completed work is installed only if session identity and generation still match. Closing invalidates that session's render tokens. A stale render cannot repopulate a closed/new preview, enable its buttons, or initiate clipboard/save work.

Raster transport has explicit width, height, pixel layout, and immutable shared storage. Rows are tightly packed, so stride is always `width × 4` and is not carried separately. The layout is opaque 32-bit, equivalent to `QImage::Format_RGB32`. The renderer allocates the shared buffer first and paints through a QImage wrapping it, so no full-buffer copy is needed and allocation failure is a caught render failure rather than a null image. Adapters wrap the same storage while preserving lifetime and using the declared representation. The published clipboard image outlives its output operation, so that wrapper keeps the storage alive through its cleanup function. Conversion, if needed, is an accounted allocation. The transport never borrows a worker-local QImage buffer or carries a QObject across layers.

There is no capture schema migration or persisted capture preference. Existing profile, benchmark, and graph-configuration schemas and ownership remain unchanged. Session state is discarded on Close or destination confirmation; output operation state ends after completion. Only the user-requested PNG and clipboard content escape that lifetime. Clipboard pixels stay in memory until the clipboard is replaced or flushed at exit.

## Failure and quality behavior

### Rendering and responsiveness

Qt documents [QPainter painting to QImage in worker threads](https://doc.qt.io/qt-6/threads-modules.html#painting-in-threads). Workers receive detached snapshot values and paint separate images; they never call live QQuickItem or view-model methods. The UI thread takes the value snapshot and presents completed results; image layout and rendering run separately so that work does not hold up the app. Worker-owned measurement/font objects and paint devices are not concurrently mutated.

Painting uses the final raster size and a consistent logical-to-pixel transform. Text, strokes, borders, markers, and paths are rasterized at that size. Do not render at 100% and enlarge the bitmap, or let the preview fit scale become an input to rendering. Use logical font sizes and density once; avoid multiplying output by monitor device-pixel ratio a second time. Percentage-only changes preserve logical marker-density/layout decisions and the selected data/bounds. Aspect changes can rearrange layout under the same content guarantees. Layout is measured once for a reference, under one stable logical coordinate and DPI policy, and its line breaks are stored in the item list, so a resolution change cannot rewrap text. Capture fonts use `QFont::PreferNoHinting`, so logical metrics stay linear when scaled, and `QFont::NoSubpixelAntialias`, because colour fringes worsen when recipients rescale an image. Workers build their fonts from captured descriptions rather than sharing `QFont` objects with the GUI thread. Tests assert the item list is unchanged across resolutions, and the validation gate confirms these font settings on rendered output.

The preview fits or scrolls an image presentation derived from the successful raster. Fit/downsampling affects display only. Long/wide tables have keyboard-operable navigation through their full extent, with dimensions and controls outside that extent and a reachable fixed action footer. Dialog resizing changes fit/navigation, never output dimensions. An invalid edit clears even an already displayed preview. A stale image may remain only while a valid replacement renders, and it never enables output.

Rendering runs on a dedicated `QThreadPool` capped at one thread and owned by the capture coordinator, with one running request and one pending slot that newer requests replace, not an unbounded queue of images. PNG saves run on a separate single-thread pool owned by the output use case. Qt Concurrent is not added. The capture coordinator guards duplicate preparation, and the output use case owns global admission, so only one output attempt is admitted at a time across targets. Controls are not disabled because another output is running; a rejected action follows the rule under [Quick copy](#quick-copy). No in-progress state is shown for Copy or PNG saving. Imports and live updates continue throughout. A submitted save does not depend on the preview's lifetime.

The app closes normally through both window Close and menu Quit. After the event loop ends, teardown waits for any accepted PNG save, which needs no GUI callback: the output use case joins its worker in its destructor. View models are QObject children destroyed after App's members, so completion is posted through a context object and dropped when nothing remains to receive it. A save failure during exit is not reported, and QSaveFile leaves the existing destination intact. Unsubmitted render work can be discarded at shutdown.

PNG encoding/file work runs off the GUI thread. Qt clipboard publication occurs on the GUI thread, and on-demand conversion is expected to be served there too. Qt limits publication to three attempts with 100 ms sleeps, which does not bound the operating-system calls themselves. The platform gate must measure UI responsiveness during contention, ordinary copies, and pasting a large image with Windows clipboard history enabled: background rasterization alone does not prove clipboard responsiveness. If the Qt candidate fails that gate, first try `OleFlushClipboard` straight after the ownership check, which moves conversion to copy time, then a Win32 publisher on a worker thread. No private Qt hook or console-log scraping is part of the contract.

### Practical resource policy and unresolved evidence gate

Validate logical layout, final dimensions, per-axis limits, pixel area, buffer arithmetic, source geometry cost, and a conservative memory estimate before committing to expensive work. Arithmetic uses checked wide intermediates. The estimate is an admission check, not a prediction of process peak memory. It includes source snapshot/geometry, current raster, any in-flight replacement, display thumbnail, encoder/conversion storage, and clipboard pixels retained after output completes; a width/height cap alone is insufficient. PNG may stream to the temporary destination rather than build another full encoded buffer.

The policy is a named, injectable set of limits shared by quick copy and preview. Report the violated constraint and useful correction: reduce graph dimensions or resolution; reduce table resolution; or explain when complete table content exceeds support even at 50%. Do not clamp, silently lower density, omit content, or split images. Allocation or painting failures after preflight follow the same recoverable render-failure state.

**Unresolved before feature acceptance:** numerical dimension/area/memory limits, representative render/copy/paste/save latency, and the concrete standard graph reference size. Validate these as part of implementing the complete feature using supported Windows/Qt settings and representative dense graphs, long labels, large tables, and many-tier benchmarks. Record hardware/runtime, input scale, actual dimensions, peak memory, responsiveness, and the readability/detail result. Publish the resulting limits through validation and documentation. These checks form the completion gate for the whole feature. This proposal does not claim measurements or validated limits. Normal target content failing complete-content or fresh-rendering requirements requires revisiting the design/scope, not weakening those requirements in implementation.

### Feedback, accessibility, and recovery

The main status area composes import and capture state independently. An unresolved import warning remains visible and retains Details/dismiss access when a capture result arrives. The footer stays visible when idle, so capture feedback never changes live viewport geometry or scroll position as it appears or clears. This removes the bar's current hidden mode and adds a permanent strip to every view. Import and capture status share that footer, side by side, and elide rather than stack at constrained widths; do not replace one unresolved warning with another notice. Capture successes name the target and expire after approximately four seconds of visible presentation. Capture failures remain dismissible and distinguishable by text/icon as well as colour.

While the preview remains open, its footer area presents the same capture status state and dismiss action, with an accessible announcement. This is one notification mirrored into the active context, not a second failure workflow or a new modal alert. After Export dismisses the preview, the main status bar continues that state. Status messages identify Copy versus Export and the target; a dismissed preview cannot consume and lose the result.

Associate malformed/unsupported dimension errors with inputs and the unavailable image state. Keep raw invalid text for correction. Render failures have an explicit retry affordance over the same snapshot/options. Clipboard failure retains an open preview's image; retry copies that image. Save failure has no automatic reopening or hidden retry session. Reopening from the target obtains new content/defaults.

Capture controls and menus have target-specific accessible names, tooltips, keyboard activation, visible focus, and ordinary Escape behavior. Preview Copy uses the required accessible name. Focus stays in the preview after Copy and returns to a surviving origin on Close or destination confirmation; otherwise use the owning workspace as fallback. Scrollable controls, full-image navigation, and the footer remain reachable at supported window/text scales.

No upload, telemetry, source mutation, unrelated panel capture, or capture-preference write is introduced. PNG metadata and titles must not contain source paths or unrelated profile details. The opaque captured appearance is the current app appearance; alternate themes, transparency, and other formats remain outside scope.

## Architectural decisions

The owner adopted the following choices for this proposal:

- A dedicated C++ renderer over a value snapshot, sharing graph-painting behavior with the live app; separate export table layout and painting are an accepted maintenance cost. Offscreen QML export layouts were rejected. The live table stays in QML, and moving it to C++ painting is left until a large style change justifies it.
- The live `GraphCanvas` paints through the same value `GraphScene` capture uses, and the canvas is the source of effective graph state for all six graphs. Per-target graph adapters were rejected.
- Layout is measured once in logical units into a flat item list that painting replays at scale. Measuring again at each output size was rejected.
- Table rows gain one typed form, and display strings built in QML move into the presentation model.
- Exported thresholds sit in their own lane under each bar. Porting `TierBar`'s label placement was rejected, and the owner approved the rendered result.
- Capture fonts use no hinting and no subpixel antialiasing from the start, rather than waiting for tests to show a need.
- Rendering and saving each use a single-thread `QThreadPool`; Qt Concurrent is not added.
- Presentation owns the snapshot and capture session; application use cases own output operations through injectable adapters; render workers consume immutable values.
- A standard graph export layout independent of the live widget provides the initial reference size. Starting from the live widget's dimensions was rejected.
- Preview Copy retains the visit and uses the reviewed image with the same result feedback as quick copy. Locking the preview until output finishes was rejected.
- Confirming a PNG destination immediately dismisses the preview; background save failure is reported in the main status bar without reopening it.
- One output operation at a time, feedback visible while the preview is open, verified clipboard publication, and atomic PNG replacement.
- No in-progress state for Copy or PNG saving: users see the final result, and duplicate prevention remains.
- The preview is window-modal.
- Closing the app during a save exits normally, with teardown waiting for the save; a failure at that point goes unreported.
- Implement the feature as a whole, with rendering/resource evidence and supported limits established before completion is accepted.

ADR 0001 and ADR 0004 govern contract placement and application behavior. Presentation snapshot/render helpers are presentation-only collaborators, not new service access to accepted profile or benchmark state. ADR 0005 and ADR 0006 continue governing those existing authorities; capture changes none of their persistence or editing rules.

**ADR recommended:** Record the durable boundary between presentation-owned render snapshots and application-owned output jobs. It introduces a reusable precedent for exporting presentation state across layer/thread boundaries without coupling application contracts to live QML or view models. The decision is fully described here; no ADR is created by this workflow.

## Risks, trade-offs, and implementation latitude

- The table is implemented twice. Typed rows and shared strings keep values and text in one place, and the threshold lane removes label placement from export, but export still repaints chunks, fills, hatching, markers, and colour rules in C++, so table style changes must be made in both places. This is accepted because the table is expected to change rarely. A large style change is the point to consider moving the live table to C++ painting. The parity test catches information missing from export, not style differences.
- Sharing graph rendering changes a mature code path, which every live paint now takes. Preserve paint order, each series' mapping, carry/observation separation, references, clipping, and marker rules through existing and added tests. The canvas already allocates display points on every paint, so building a scene is expected to cost little, but dense graphs must confirm it.
- The threshold lane makes exported bars look different from live ones and makes rows taller.
- The always-visible footer is the one change seen by people who never use captures, and it costs 26 pixels of mostly empty bar on every view.
- Adding non-null output leaves touches every injected `App` call site: the gallery, `ksv_driver`, and the integration suite's fixtures.
- Copying large data sets into a snapshot and rendering large images both consume resources. Immutable sharing may avoid deep copies only when no mutable/live-owned storage or formatter capture remains reachable. Validate snapshot creation as part of the responsiveness requirement; it must remain a quick value read rather than a visible interruption.
- Clipboard ownership verification proves publication at the observed point, not future ownership, later on-demand conversion, or what another application will do to a pasted image. Normal exit flushes the clipboard, so a large copy can slow exit, and an abnormal exit can lose formats not yet converted. Windows adapter behavior and contention remain validation risks; no unconditional rollback or recipient thumbnail-size guarantee is made.
- Safe PNG replacement intentionally rejects destinations where its temporary-write/commit strategy cannot succeed. It does not fall back to destructive direct overwrite merely to finish.
- Save failure no longer preserves a preview visit. This is an explicit product trade-off for immediate dismissal; a new attempt captures current content with defaults. Copy retains its visit.
- Removing the in-progress state means a long save shows nothing until its result, and closing the app during a save leaves the process running without a window until the write finishes. A failure at that point goes unreported.
- Concrete reference dimensions, measured resource caps, and latency evidence remain open until implementation validation. They are completion criteria for the whole feature, not permission to silently choose limits that exclude normal target content.

Implementation may choose helper names, pixel conversion details, graph legend placement, readable table wrapping rules, image-provider/thumbnail mechanics, PNG filename suggestions, initial save directory, exact date wording, and the arrangement of shared feedback. These choices must preserve the stated ownership, output lifecycle, sizing model, complete-content guarantees, accessible feedback, and resource policy. Altering those material decisions returns for design review.
